Architektura bezpiecznego renderowania LaTeX i Markdown w aplikacjach webowych: Wektory ataków, inżynieria potoku i deterministyczny sandboxingPrzetwarzanie i renderowanie niezaufanego kodu matematycznego oraz tekstu formatowanego w środowisku przeglądarki internetowej stawia przed inżynierami oprogramowania wyzwania wykraczające poza standardowe mechanizmy obrony aplikacji webowych. Integracja deklaratywnych silników Markdown, takich jak marked, z wyspecjalizowanymi parserami i kompilatorami notacji matematycznej (KaTeX, MathJax, LaTeX.js) tworzy wysoce złożony system interpretacji danych. W takim ekosystemie spotykają się odmienne paradygmaty: parsowanie gramatyk bezkontekstowych, dynamiczne rozwijanie makr o kompletności w sensie Turinga oraz wielojęzyczne drzewa dokumentów łączące przestrzenie nazw HTML, SVG i MathML.Niewłaściwa integracja tych technologii otwiera szeroką przestrzeń dla ataków odmowy usługi (zarówno w postaci katastrofalnych nawrotów w silnikach wyrażeń regularnych, jak i bomb pamięciowych w ekspanderach makr) oraz zaawansowanych ataków typu Cross-Site Scripting (XSS), w tym mutacyjnego XSS (mXSS) wynikającego z tzw. pomylenia przestrzeni nazw (Namespace Confusion). Zbudowanie bezpiecznego potoku przetwarzania wymaga wielowarstwowej strategii obrony w głąb (Defense-in-Depth), łączącej ścisłą sekwencyjność leksykalną, utwardzoną sanitizację oraz twardą izolację procesową wspieraną przez deterministyczne egzekwowanie budżetu czasu procesora.1. Wektory podatności w parserach matematycznych i silnikach MarkdownPodatności ReDoS w tokenizatorach i parserach formułZjawisko Regular Expression Denial of Service (ReDoS) wynika bezpośrednio z mechaniki algorytmicznej powszechnie stosowanej w silnikach wyrażeń regularnych nowoczesnych środowisk wykonawczych JavaScript, takich jak Irregexp w silniku V8. Silniki te opierają się głównie na symulacji niedeterministycznych automatów skończonych ze stosem nawrotów (Spencer's backtracking NFA). Choć podejście to oferuje wysoką ekspresję i wsparcie dla rozszerzeń gramatycznych, charakteryzuje się pesymistyczną złożonością czasową, która przy wystąpieniu wieloznaczności w strukturze wyrażenia regularnego degraduje się ze stałej lub liniowej do wielomianowej $\mathcal{O}(n^k)$, a w skrajnych przypadkach wykładniczej $\mathcal{O}(2^n)$ względem długości ciągu wejściowego $n$.Podatności te występują regularnie w parserach tekstu formatowanego; biblioteka marked wielokrotnie borykała się z problemami katastrofalnego nawrotu, czego przykładem były luki CVE-2021-21306 oraz CVE-2022-21680 związane ze złożonością wyrażenia block.def. Poważniejsze zagrożenie pojawia się jednak na styku Markdownu i formuł matematycznych, gdzie programiści implementują naiwne wyrażenia regularne do wyodrębniania bloków $...$ lub $$...$$. Wzorzec ze zagnieżdżonymi kwantyfikatorami i alternatywami nakładającymi się leksykalnie (np. próba dopasowania znaków ucieczki obok znaków nielimitowanych) w zderzeniu ze złośliwie spreparowanym, niezbalansowanym ciągiem wejściowym zmusza silnik regex do przeszukania potężnego drzewa permutacji ścieżek dopasowania. W rezultacie pojedynczy ciąg o długości kilkudziesięciu znaków potrafi zawiesić wątek wykonawczy przeglądarki na wiele minut.W przypadku środowiska LaTeX.js wektor ten przyjmuje nieco inny wymiar architektoniczny. Biblioteka opiera się na generatorze parserów PEG.js (Parsing Expression Grammar), który przetwarza gramatykę bez nawrotów wykładniczych dzięki technice memoizacji (algorytm Packrata). Zabezpieczenie przed czasem wykładniczym okupione jest jednak gwarantowaną liniową złożonością pamięciową $\mathcal{O}(n)$ względem rozmiaru wejścia i głębokości reguł. Złożone formuły o ekstremalnym zagnieżdżeniu środowisk matematycznych prowadzą w parserze PEG do wyczerpania stosu wywołań silnika JavaScript (Maximum call stack size exceeded) bądź alokacji gigabajtowych tablic memoizacyjnych, co wywołuje błąd braku pamięci (Out-Of-Memory crash) i awaryjne zamknięcie procesu karty.Manipulacja przestrzeniami nazw i eskalacja uprawnień przez MathML oraz SVGGenerowanie kodu MathML i wektorów SVG w celu prezentacji typografii matematycznej rodzi ryzyko wstrzyknięcia złośliwego kodu JavaScript. Podstawowy wektor stanowią interaktywne elementy i atrybuty zdefiniowane w samych specyfikacjach formatów wizualnych. Format MathML definiuje element <maction>, którego zadaniem jest obsługa dynamicznych akcji, co historycznie pozwalało na uruchamianie skryptów, a atrybuty href oraz xlink:href w MathML i SVG umożliwiają osadzanie pseudo-protokołów javascript: lub data:. Jeżeli parser matematyczny nie zweryfikuje protokołu przekazanego do komendy \href, silnik wygeneruje bezpośrednio klikalny element z aktywnym ładunkiem wykonawczym.Zjawiskiem o znacznie wyższym stopniu złożoności jest mutacyjny XSS (mXSS), wywoływany przez błędy pomylenia przestrzeni nazw (Namespace Confusion). Zgodnie ze standardem parsowania HTML5 węzły w drzewie DOM dziedziczą przestrzeń nazw po rodzicu, jednak elementy <math> oraz <svg> wprowadzają stan obcej zawartości (foreign content). W tej obcej przestrzeni reguły leksemów diametralnie różnią się od reguł HTML; przykładowo znacznik <style> w przestrzeni HTML jest elementem typu rawtext (który nie może posiadać dzieci w drzewie DOM), podczas gdy wewnątrz SVG czy MathML jest traktowany jak standardowy element kontenerowy. Standard przewiduje precyzyjnie zdefiniowane punkty integracji HTML (HTML Integration Points), które przełączają parser z powrotem do przestrzeni HTML. Są to m.in. <svg foreignObject>, <svg desc>, <svg title> oraz <math annotation-xml> pod warunkiem posiadania atrybutu encoding="text/html" lub encoding="application/xhtml+xml". Ponadto istnieją punkty integracji tekstu MathML (<mi>, <mo>, <mn>, <ms>, <mtext>).Atak mXSS wykorzystuje asymetrię między początkowym parsowaniem a ponowną serializacją do tekstu: złośliwy kod wejściowy buduje początkowo drzewo DOM uznawane przez sanitizer za całkowicie bezpieczne (ponieważ złośliwe znaczniki ukryte są np. wewnątrz atrybutów lub w nieszkodliwej przestrzeni obcej). Gdy jednak takie drzewo zostanie zserializowane przez przypisanie do innerHTML, a następnie powtórnie sparsowane przez przeglądarkę, elementy pomocnicze wymuszają ucieczkę z przestrzeni MathML/SVG do przestrzeni HTML. W konsekwencji element uznawany dotąd za ciąg znaków wewnątrz atrybutu zostaje zinterpretowany jako aktywny tag HTML z handlerem zdarzeń, np. <img src=x onerror=alert(1)>.Dodatkowym zagrożeniem są błędy w samych implementacjach silników LaTeX. Biblioteka KaTeX w trybie domyślnym odrzuca polecenia zagrażające bezpieczeństwu, lecz włączenie flagi trust: true bez rygorystycznej funkcji weryfikującej otwiera krytyczne podatności. W podatności CVE-2025-23207 wykazano, że komenda \htmlData nie sprawdzała poprawności nazw atrybutów, co pozwalało na domknięcie cudzysłowu i zdefiniowanie dowolnego handlera zdarzeń w wyjściowym kodzie HTML. Z kolei podatność GHSA-f98w-7cxr-ff2h dotyczyła braku ucieczki znaków w poleceniu \includegraphics, co umożliwiało przełamanie atrybutów znacznika graficznego. Istotnym błędem po stronie aplikacji integrujących jest również bezpośrednie wstrzykiwanie treści obiektów błędów parsera. W KaTeX instancja ParseError zawiera w polu message surowy, niesparsowany fragment wejścia LaTeX. Wstawienie komunikatu o błędzie do drzewa za pomocą właściwości innerHTML zamiast innerText lub textContent skutkuje natychmiastowym wykonaniem zawartego w błędnej formule ładunku XSS.Odmowa usługi przez rekurencję i bomby makrSystem makr wbudowany w standard TeX posiada moc obliczeniową maszyny Turinga, co sprawia, że biblioteki wiernie odwzorowujące te mechanizmy są domyślnie podatne na celowe ataki paraliżujące zasoby obliczeniowe środowiska wykonawczego. Podstawowym wektorem jest rekurencja nieskończona, realizowana przez komendy pokroju \def\x{\x} \x. Silnik pozbawiony restrykcyjnych liczników wywołań wchodzi w pętlę generowania tokenów, doprowadzając do zablokowania jednowątkowej pętli zdarzeń JavaScript lub natychmiastowego przepełnienia stosu wywołań.Groźniejszą formą ataku jest bomba dekompresyjna makr (ang. Architektura potoku przetwarzania i integracja z sanitizacją DOMSekwencyjność leksykalna: Wzorzec tokenów zastępczychPrzetwarzanie tekstu zawierającego jednocześnie znaczniki Markdown oraz kod matematyczny LaTeX wymaga wyeliminowania wzajemnej destrukcji struktur leksykalnych. Zastosowanie potoku, w którym Markdown jest kompilowany w pierwszej kolejności, prowadzi do uszkodzenia kodu LaTeX: parser Markdown traktuje znaki podkreślenia (_) w indeksach dolnych oraz gwiazdki (*) w operacjach algebraicznych jako formatowanie kursywy lub pogrubienia. W efekcie wyrażenie $x_i * y_i * z_i$ zostaje przekształcone w $x<em>i * y</em>i * z_i$, co niszczy składnię formuły i powoduje błąd kompilacji matematycznej. Z kolei próba przetworzenia kodu LaTeX na kod HTML/MathML przed kompilacją Markdownu skutkuje tym, że wcięcia i znaki nowej linii w wygenerowanych strukturach XML są interpretowane przez silnik Markdown jako bloki kodu źródłowego (<pre><code>), co destabilizuje strukturę dokumentu i ułatwia wstrzyknięcie zniekształconych ładunków mXSS.Prawidłowa inżynieria potoku wymaga zastosowania wzorca ekstrakcji leksykalnej z kryptograficznymi tokenami zastępczymi (Placeholder Nonce Pattern). W pierwszej fazie potoku surowy tekst wejściowy jest analizowany wyłącznie w celu identyfikacji i wycięcia bloków matematycznych (zarówno blokowych $$...$$, jak i wierszowych $...$). W miejsce wyciętych formuł wstawiane są unikalne, alfanumeryczne ciągi zastępcze (np. TOKENMATHTOKENa8f9c1...), generowane przy użyciu generatora liczb pseudolosowych o wysokiej entropii (crypto.randomUUID()). Tokeny te nie mogą zawierać żadnych znaków zastrzeżonych dla składni Markdown ani sekwencji formatujących.W drugiej fazie zabezpieczony tekst – pozbawiony znaków LaTeX – trafia do parsera marked, który kompiluje strukturę akapitów, list i nagłówków. W fazie trzeciej wyekstrahowane bloki LaTeX są kompilowane w środowisku o zaostrzonych limitach do formatu MathML lub bezpiecznego HTML. Faza czwarta polega na podstawieniu wygenerowanych fragmentów matematycznych w miejsca odpowiadających im tokenów w wyjściowym kodzie HTML. W fazie piątej, stanowiącej ostateczne domknięcie potoku, zrekonstruowany dokument HTML jest przekazywany do biblioteki DOMPurify. Sanitizacja musi bezwzględnie stanowić ostatni krok przed wstrzyknięciem danych do właściwego węzła DOM; jakiekolwiek przetwarzanie łańcuchów znaków po procesie sanitizacji niweczy gwarancje bezpieczeństwa.Konfiguracja i utwardzanie DOMPurify wobec mXSSDomyślna konfiguracja biblioteki DOMPurify dopuszcza znaczniki SVG i MathML, co przy braku odpowiedniego profilowania może narazić aplikację na zniekształcenia parsowania typu Namespace Confusion. Zapewnienie pełnej odporności na ataki mXSS w dokumentach matematycznych wymaga wdrożenia rygorystycznych reguł sanitizacji.Przede wszystkim należy wyeliminować wszelkie elementy działające jako punkty integracji HTML w przestrzeniach obcych. Bezwzględnie blokowany musi być znacznik <foreignObject>, który pozwala na bezpośrednie osadzanie standardowych struktur HTML wewnątrz wektorów SVG. W kontekście MathML konieczne jest wykluczenie znacznika <annotation-xml>, który przy określonych atrybutach kodowania resetuje przestrzeń nazw do standardu HTML, stając się źródłem mutacji w parserach silników przeglądarek. Dodatkowo należy zablokować element <maction> oraz zakazać używania atrybutów xlink:href i href na elementach matematycznych i wektorowych, co eliminuje możliwość wykonania kodu poprzez manipulację odnośnikami.Kolejnym wymogiem jest wymuszenie flagi SAFE_FOR_XML: true. Opcja ta nakłada na sanitizer obowiązek sprawdzania, czy wartości atrybutów nie zawierają ukrytych sekwencji domykających komentarze, sekcje CDATA lub elementy tekstowe, co uniemożliwia rozbicie kontekstu XML podczas ponownego parsowania. Architektura izolacji i deterministyczny budżet zasobów CPUOgraniczenia asynchroniczności i wymuszone przerywaniePoważnym wyzwaniem w zapobieganiu atakom DoS w architekturze przeglądarkowej jest jednowątkowa natura środowiska wykonawczego JavaScript, oparta na modelu Run-to-Completion. Jeżeli parser wejdzie w stan katastrofalnego nawrotu wyrażenia regularnego lub głębokiej pętli rozwijania makr, wątek zostaje zablokowany synchronicznie.Popularny mechanizm AbortController i odpowiadający mu obiekt AbortSignal są całkowicie nieskuteczne w walce z tym zjawiskiem. Model działania AbortSignal opiera się na wywłaszczaniu kooperatywnym: wykonywany kod musi w regularnych odstępach czasu odpytywać stan właściwości signal.aborted i dobrowolnie przerwać swoje działanie poprzez zgłoszenie wyjątku. Rdzenne algorytmy wyrażeń regularnych w silniku V8 oraz wewnętrzne pętle kompilatorów KaTeX, MathJax i PEG.js nie implementują sprawdzania flagi przerwania w trakcie synchronicznych operacji dopasowywania tekstu. Wywołanie metody abort() w wątku głównym nie wywiera zatem żadnego wpływu na trwający paraliż procesora.Jedynym deterministycznym mechanizmem wymuszenia twardego budżetu czasu procesora jest przeniesienie operacji parsowania do dedykowanego wątku Web Worker i wykorzystanie metody Worker.prototype.terminate(). Wywołanie terminate() niszczy natychmiast cały kontekst wykonawczy wątku (odpowiadający strukturze V8 Isolate) na poziomie systemowym, natychmiastowo zwalniając rdzeń procesora i alokowaną pamięć operacyjną.Podział odpowiedzialności między Web Worker a wątek głównyWdrożenie wątku roboczego wymaga uwzględnienia ograniczeń środowiska DedicatedWorkerGlobalScope. W kontekście tym nie istnieją obiekty window ani interfejsy drzewa dokumentu (document, HTMLElement), co uniemożliwia bezpośrednie manipulowanie interfejsem użytkownika.Kompilatory KaTeX oraz silnik Markdown marked są w stanie funkcjonować wewnątrz Web Workera w trybie generowania czystych łańcuchów znaków (np. za pośrednictwem metody katex.renderToString()). Z kolei biblioteka DOMPurify do poprawnego działania wymaga dostępu do natywnego parsera drzewa DOM przeglądarki. Uruchomienie DOMPurify wewnątrz Workera wymagałoby dostarczenia emulacji DOM, takiej jak jsdom, co pociąga za sobą drastyczny narzut pamięciowy (kilkanaście megabajtów zależności) oraz znaczną degradację czasu przetwarzania.Optymalny podział ról polega na delegowaniu do Web Workera operacji leksykalnych, wyodrębniania tokenów, kompilacji Markdownu oraz renderowania kodu LaTeX do surowego ciągu HTML/MathML. Tak wygenerowany ciąg tekstowy jest przesyłany z powrotem do wątku głównego, gdzie podlega natychmiastowej sanitizacji przez DOMPurify z wykorzystaniem wysoce zoptymalizowanego, natywnego środowiska przeglądarki.Twarde piaskowanie w izolowanej ramce (Sandboxed iframe)W systemach o podwyższonym profilu bezpieczeństwa – na przykład na platformach edycyjnych renderujących pełne, zdefiniowane przez użytkowników dokumenty przy użyciu LaTeX.js – sanitizacja kodu może okazać się niewystarczająca wobec potencjalnych podatności typu zero-day w silnikach przeglądarek. W takich scenariuszach architekturę należy rozszerzyć o twardy sandboxing za pomocą elementu <iframe>.Bezpieczna implementacja ramki izolującej wymaga spełnienia ściśle określonych warunków:Po pierwsze, element musi posiadać atrybut sandbox="allow-scripts", przy czym bezwzględnie zabronione jest dołączanie flagi allow-same-origin. Brak uprawnienia do wspólnego pochodzenia wymusza traktowanie zawartości ramki jako nieprzeniknionego, unikalnego pochodzenia nieprzezroczystego (origin: null). Implementacja produkcyjna: Watchdog budżetu CPU i silnik renderującyPoniższy kod źródłowy w języku TypeScript przedstawia produkcyjną implementację potoku renderowania. Architektura ta wykorzystuje dedykowany wątek Web Worker do kompilacji, egzekwuje twardy limit czasu procesora (300 ms na wpis) z automatyczną terminacją zablokowanego wątku oraz realizuje sanitizację wyjściową w wątku głównym z wykorzystaniem biblioteki DOMPurify.Kod wątku wykonawczego (render.worker.ts)Wątek roboczy przyjmuje niezaufany ciąg wejściowy, realizuje leksykalną ekstrakcję formuł matematycznych przy użyciu alfanumerycznych tokenów zastępczych, przetwarza Markdown, renderuje formuły LaTeX z zachowaniem restrykcyjnych limitów KaTeX i odsyła wynikowy ciąg tekstowy.TypeScriptimport katex from 'katex';
import { marked } from 'marked';

interface RenderRequest {
  id: string;
  markdownPayload: string;
}

interface RenderResponse {
  id: string;
  html?: string;
  error?: string;
}

self.onmessage = (event: MessageEvent<RenderRequest>) => {
  const { id, markdownPayload } = event.data;

  try {
    const mathRegistry = new Map<string, { formula: string; isDisplay: boolean }>();
    let counter = 0;

    // Faza 1: Liniowe wyodrębnienie bloków matematycznych za pomocą unikalnych tokenów
    const textWithoutDisplayMath = markdownPayload.replace(
      /\$\$([\s\S]*?)\$\$/g,
      (_, formula) => {
        const token = `MATHNONCEDISPLAY${counter++}XYZ`;
        mathRegistry.set(token, { formula, isDisplay: true });
        return token;
      }
    );

    const safeTextOnly = textWithoutDisplayMath.replace(
      /\$([^\$\n]+)\$/g,
      (_, formula) => {
        const token = `MATHNONCEINLINE${counter++}XYZ`;
        mathRegistry.set(token, { formula, isDisplay: false });
        return token;
      }
    );

    // Faza 2: Kompilacja struktury Markdown na bezpiecznym ciągu znaków
    let compiledMarkup = marked.parse(safeTextOnly, { async: false }) as string;

    // Faza 3 i 4: Kompilacja formuł LaTeX z nałożonymi limitami bezpieczeństwa
    mathRegistry.forEach((spec, token) => {
      let renderedFormula = '';
      try {
        renderedFormula = katex.renderToString(spec.formula, {
          displayMode: spec.isDisplay,
          throwOnError: true,
          trust: false,       // Bezwzględna blokada poleceń URL/HTML (np. \href, \htmlData)
          maxExpand: 50,      // Ochrona przed bombami dekompresyjnymi makr
          maxSize: 15,        // Ochrona przed Visual Layout DoS
          strict: 'error'     // Blokada niestandardowych, podatnych rozszerzeń
        });
      } catch {
        // Zabezpieczenie przed ParseError reflection: błąd nie zawiera kodu wejściowego
        renderedFormula = '<span class="formula-error">[Błąd renderowania formuły]</span>';
      }
      compiledMarkup = compiledMarkup.replace(token, renderedFormula);
    });

    // Wysłanie surowego ciągu HTML/MathML z powrotem do zarządcy w wątku głównym
    self.postMessage({ id, html: compiledMarkup } as RenderResponse);
  } catch (executionError: unknown) {
    const errorMessage = executionError instanceof Error ? executionError.message : 'Nieznany błąd workera';
    self.postMessage({ id, error: errorMessage } as RenderResponse);
  }
};
Kod silnika nadrzędnego w wątku głównym (SecureRenderEngine.ts)Klasa SecureRenderEngine zarządza cyklem życia wątku roboczego, monitoruje czas wykonania za pomocą twardego watchdoga zegarowego, niszczy proces V8 Isolate w przypadku przekroczenia budżetu CPU oraz przeprowadza ostateczną sanitizację za pomocą DOMPurify.TypeScriptimport DOMPurify from 'dompurify';

export class SecureRenderEngine {
  private worker: Worker | null = null;
  private readonly workerUrl: string;

  constructor(workerUrl: string) {
    this.workerUrl = workerUrl;
    this.spawnWorker();
  }

  private spawnWorker(): void {
    if (this.worker) {
      this.worker.terminate();
    }
    this.worker = new Worker(this.workerUrl, { type: 'module' });
  }

  public async renderUntrustedContent(
    untrustedMarkdown: string,
    cpuBudgetMs: number = 300
  ): Promise<string> {
    return new Promise((resolve, reject) => {
      const taskId = crypto.randomUUID();
      let timer: number | null = null;

      const clearExecution = () => {
        if (timer !== null) {
          window.clearTimeout(timer);
          timer = null;
        }
        if (this.worker) {
          this.worker.removeEventListener('message', onMessage);
          this.worker.removeEventListener('error', onError);
        }
      };

      // Twardy watchdog zegarowy egzekwujący budżet CPU
      timer = window.setTimeout(() => {
        clearExecution();
        // Wymuszone zniszczenie wątku paraliżującego procesor (ReDoS / Makro DoS)
        this.spawnWorker();
        reject(
          new Error(
            `Przekroczono twardy budżet czasu procesora (${cpuBudgetMs} ms). Zadanie unieważnione.`
          )
        );
      }, cpuBudgetMs);

      const onMessage = (event: MessageEvent<{ id: string; html?: string; error?: string }>) => {
        if (event.data.id !== taskId) return;
        clearExecution();

        if (event.data.error) {
          reject(new Error(`Błąd przetwarzania: ${event.data.error}`));
          return;
        }

        try {
          // Faza 5: Ostateczna sanitizacja DOMPurify z blokadą punktów integracji i mXSS
          const sanitizedOutput = DOMPurify.sanitize(event.data.html || '', {
            USE_PROFILES: { html: true, mathMl: true, svg: true },
            FORBID_TAGS: ['foreignObject', 'annotation-xml', 'maction'],
            FORBID_ATTR: ['xlink:href', 'href', 'actiontype', 'onfocus', 'onerror'],
            SAFE_FOR_XML: true,
            ALLOW_DATA_ATTR: false
          });
          resolve(sanitizedOutput);
        } catch (sanitizerError) {
          reject(sanitizerError);
        }
      };

      const onError = (error: ErrorEvent) => {
        clearExecution();
        this.spawnWorker();
        reject(new Error(`Krytyczna awaria środowiska wykonawczego: ${error.message}`));
      };

      if (!this.worker) {
        this.spawnWorker();
      }

      this.worker!.addEventListener('message', onMessage);
      this.worker!.addEventListener('error', onError);

      this.worker!.postMessage({
        id: taskId,
        markdownPayload: untrustedMarkdown
      });
    });
  }

  public destroy(): void {
    if (this.worker) {
      this.worker.terminate();
      this.worker = null;
    }
  }
}
